# T-084 — report

## Outcome

Reading a Series page no longer stores anywhere to come back to. Pressing
**Have a password? Sign in instead.** does, through a new GET route that
stores the page and then shows sign-in. A sign-in link returns somebody to
what their browser was holding only when that browser asked for that account's
link; otherwise the link forgets both keys and lands on the account's own
landing. The code sign-in on a Series page, which spent neither key, now
forgets both. So a browser that passed a Series as a guest, or was bounced to
sign-in from a Group page and left, no longer hands the next account to sign
in there a destination that was never theirs.

## Found, not fixed

- Two guests at one browser are still one browser: when the first asked to
  sign in, or was bounced from a protected page, and walked away, the second
  signing in there with a password, a passkey or a link asked for there still
  lands on the first person's page. → decided: `D-017` records it; closing it
  needs the destination to travel in the sign-in page's URL rather than the
  session, which reverses `T-008`'s second key and rewrites every path that
  stores one.
- A named destination still outlives a verified sign-in that spends
  `url.intended`. → decided: nothing reads it for a verified person except a
  re-opened verification link, which returns them to the page they themselves
  asked for, and signing out empties the session.
- The sign-in form could not be driven by synthetic typing in the browser
  pane: a click on the field and typed keys never reached the Vue input, so
  the final walk posted the link request from the page's own session instead.
  → decided: a harness limit, not the product — `SignInCompositionTest` covers
  the two steps and `T-087` walked them by hand.
