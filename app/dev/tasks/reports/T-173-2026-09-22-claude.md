# T-173 — report

## Outcome

Staff now make plan vouchers in Qori's console, and Qori creates the Stripe
coupon itself, named by its code. A voucher is always a percentage off; an
amount off is refused, because it would pull a fixed-price buyer back to AUD.
Changing a voucher's percentage, duration, months, cap or expiry makes a new
coupon and deletes the old one, since Stripe will not edit them. Retiring a
voucher deletes its coupon, and buyers already using it keep their discount.
The code a buyer types is still matched and counted by Qori.

## Where the specification was wrong

| Section | Said | Actually |
| --- | --- | --- |
| Decisions | "Changing only `is_active` retires or restores the voucher without replacing it" | Retiring deletes the Stripe coupon, so a restored voucher would point at nothing. Restoring publishes a new coupon. |
| Files | The controller "creates, replaces and retires coupons" | That work is `PricingService::saveCoupon()` and `retireCoupon()`, beside the price methods. See "Added during execution". |
| Scope | The form "loses amount, currency and id" | The form never had a currency input, and it had no months input either, so a repeating voucher could not be saved from it at all. The months input was added. |
| Preconditions, spike | "Create … in the local console", "Subscribe a Group with its code", `stripe invoices upcoming` | The voucher was made through the service; the subscription was made through the API with a test payment method, not by paying in a form; the invoice was previewed with `POST /v1/invoices/create_preview`, which the current API uses for an upcoming invoice. |
| Tests, case 2 | "`expires_at` is sent as a Unix time" | Right, with a catch: the date cast reads the stored time in the app's timezone, so the test compares against the model's own reading. The request also keeps the integer, not a string. |

## Departures

- The audit entry for a saved voucher records the new coupon id.
