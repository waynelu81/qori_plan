# T-093 — report

## Outcome

The free-tier pass ran from 20:49 on 19 September to 01:55 on 20 September
2026 (AEST), in Testing. The owner worked the browsers as creator and Peer,
and I made the calls with `curl`. **Step 6 as written was refused.** A
folder picked under `drive.file` does not accept a Peer's permission while
anything inside it has not been authorised for the app. That is the kill
result named under Decides. The owner then approved one extra check: pick
every item in the folder and try again. It showed the refusal is
conditional:

- **With every item beneath the folder authorised, the same call succeeds.**
  The Peer then reaches everything inside, including files added later.
- **One unauthorised item anywhere beneath the folder blocks every change to
  its sharing again**: adding a Peer, repeating a grant and removing a Peer
  alike. That item can be a file added through Drive, a file in the trash, a
  shortcut, or a file behind Limit access. The block lasts until the creator
  picks the item, moves it out, or deletes it forever.

So `D-016`'s folder grant works under `drive.file` only with a step that has
the creator pick every item beneath the folder before each sharing change. The
owner decides which design `T-094` is re-drafted on, and it is the first
bullet under Found, not fixed:

- that pick-everything step;
- per-file grants;
- the Restricted `drive` scope.

The other nine questions are answered below. There are 68 fixtures in
`tests/Fixtures/google/`, indexed in its README. The Workspace pass, steps 16
and 17, has not started; the Decisions let it trail.

## Found, not fixed

- Which design `T-094` is re-drafted on: folder grants behind a step that
  has the creator pick every item beneath the folder before each sharing
  change, per-file grants fanned out per Episode, or the Restricted `drive`
  scope with Google's security assessment. The first keeps `D-016`'s
  "a new Episode needs no new grants" only while every file in the folder is
  picked. A file the creator drops into the folder through Drive reaches the
  Peers already there, then blocks the next sale until it is picked
  → T-094
- The Picker in Safari refused with "The API developer key is invalid".
  Published reports tie that message, an empty list and a sign-in wall to a
  browser blocking the `docs.google.com` frame's cookies, which Safari, every
  browser on iOS, Chrome Incognito and Firefox's strict mode do by default.
  The picker screen needs a stated way through, and naming Google in that copy
  needs the owner's confirmation under `D-035` → T-094
- Google's "Request access" page, which any account without access reaches,
  preselects **Editor**. A creator who approves a request in Drive without
  looking gives that person edit rights, so the creator-facing copy should
  say requests are not how Peers get in → T-094
- `version` counts permission changes: it went from 4 to 42 on
  `episode.pdf` with no change to its content. `md5Checksum` is the uploaded
  bytes' MD5, and it changed only when the content did. The item check reads
  the checksum → T-094
- A pick authorises the file when the person presses Select, whether or not
  Qori receives the callback. A lost callback leaves a file granted that
  nothing in Qori records → T-094
- Picking a shortcut returns its target, and the payload's `parentId` is the
  shortcut's folder, not the target's own. The shortcut itself stays
  unauthorised and blocks the folder's sharing until it is moved out or
  deleted. Adding one prompts the creator to share the target with each
  current member of the folder, so it reaches later Peers only if shared
  again. The picker copy should say a shortcut cannot be an Episode's file
  → T-094
- The file view, `DocsView().setParent(folderId)`, lists no folders, so it
  cannot authorise a subfolder. A pick-everything step needs a view that
  shows subfolders and lets them be selected → T-094
- A folder shared with the creator by someone else comes back with no
  `parents` from `files.get` and no `parentId` in the Picker's payload. The
