# T-008 — report

## Outcome

Somebody who follows a Series link, registers, and confirms their address now
lands back on the Series instead of on a dashboard they never asked for. The
wall between those two moments also stopped being anonymous: it names the
address it wrote to, names what is waiting on the other side when there is
something, and offers a way out for whoever mistyped their address — the one
person the old screen failed hardest, because Resend only ever writes to the
same address again.

The fix is a second session key rather than a new return mechanism. The
framework's `url.intended` was never missing, it is single-use, and on the
commonest ordering Fortify's own `RegisterResponse` spends it returning the new
account to the page it registered from. That redirect is correct and is left
alone. `SignInDestination` survives it, carries the Series title alongside the
URL so the wall can name it, refuses any URL pointing off this application, and
is cleared the moment verification consumes it.

## Departures

**The verification screen renders its copy in the page body, not the layout
description.** Every other auth page hands the layout a fixed sentence through
`defineOptions`, which is evaluated once at build time. Two of this screen's
three sentences depend on who is looking at it, so they are props and they are
rendered where props can reach. The layout keeps the heading.

**`peek()` is what the screen calls, and `take()` only the response.** The spec
gives both methods and does not say which goes where. Rendering must not spend
the destination or a reload would strand whoever refreshed the page.

**The response spends the destination even when `intended()` wins.** On path B
the intended URL fires and the destination is discarded unread. That is
deliberate: the detour is over either way, and a destination left behind would
be answered by whatever interruption came next.

## Found, not fixed

**Nothing reads `?verified=1`.** The task's own Notes said so and put it out of
scope, and it is still true: verification succeeds and the page it lands on says
nothing about it. On path A that now matters less, because the Series page a
person lands on visibly changes from "Sign in to get access" to "Get access". It
needs a task.

**The "Log out" link and the wrong-address sentence say the same thing twice.**
One is a control and one is the explanation for it, which is defensible, but a
single labelled control would read better. Left alone because the Copy section
names four keys and changing the control is a composition decision, not a
wording one.
