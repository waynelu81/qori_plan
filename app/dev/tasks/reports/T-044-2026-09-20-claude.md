# T-044 — report

## Outcome

A creator can reach the Integrations page and see a Google Drive section: a
dropdown holding both of Google's tiers, and above the Connect button, for the
tier they have chosen, one recommendation sentence, at most three limitation
lines and one closed disclosure holding the rest. Pressing Connect sends them
to Google for `drive.file` alone and brings them back to a row that names the
account. Reconnecting the same account keeps the row and clears its reconnect
state; reconnecting a different one writes nothing and holds the change for ten
minutes on a page that names both accounts and offers Switch or Keep.
Disconnecting keeps the row, drops the tokens, asks Google to revoke them best
effort, and shows first what it will affect.

**Nobody has connected a real Google account through this.** Every token body
it was built and tested against is one of `T-093`'s fixtures, captured from
the OAuth 2.0 Playground, which sends no nonce and uses its own redirect. The
code exchange, PKCE and consent behaviour against Qori's own registered client
were specified from documentation. **That round trip has now been run** — the
owner signed in and pressed Allow on 20 September 2026 — and it is recorded
below under "The real round trip". `F11` is answered.

**The Google Drive section is hidden.** The owner chose this on 20 September
2026: until `T-094` adds the picker, a connected Drive holds nothing a Series
can use, and `PLAN.md`'s beta gate says no built-in action may knowingly lead
to a dead page. `GoogleAccounts` is therefore not tagged `account-connectors`,
the tag is declared empty so `ConnectionService`'s injected `$connectors` still
resolves, and `T-094` adds one line. Setup's part three shows `storage_why`
alone and no link while `ProviderSections::props()` returns no section.

## The real round trip

Run on 20 September 2026 against Qori's own registered client, on the owner's
own Google account, with the `account-connectors` tag line added locally and
not committed. The owner signed in and pressed Allow; nothing else in this
report involved a credential. This is the storage review's `F11`, and it is
answered.

**Google accepted the authorization request and rendered its own screen**,
which is itself the first result: the client id, the redirect URI and the
challenge are all registered correctly. What Qori sent, read off the
authorization URL:

| Parameter                | Value                                                 |
| ------------------------ | ----------------------------------------------------- |
| `code_challenge_method`  | `S256` — **accepted, not rejected**                   |
| `code_challenge`         | present, 43 characters                                |
| `scope`                  | `https://www.googleapis.com/auth/drive.file` alone    |
| `redirect_uri`           | `http://localhost:8001/u/connections/google/finalise` |
| `access_type`            | `offline`                                             |
| `prompt`                 | `consent`                                             |
| `include_granted_scopes` | `true`                                                |
| `login_hint`             | the owner's email                                     |

What the round trip settled, none of which `T-093`'s Playground tokens could
show, because the Playground uses its own client and its own redirect:

1. **Google takes `code_challenge` with `S256` from Qori's own client.** The
   spec's PKCE was written from documentation; it is now observed.
   `supportsPkce(): true` stops being provisional.
2. **`prompt=consent` showed the `drive.file` access and nothing else** — the
   owner's words: "consent screen just listed drive.file access". No
   per-permission checkbox was offered, which is what
   Google's granular-permissions page predicts when a request names one scope
   that is not a sign-in scope. That is the exception the Preconditions
   declared, so `tests/Fixtures/google/oauth-token-scope-declined.json` stays
   hand-edited and marked "edited, not observed", and nothing in the fixtures
   README changes.
3. **A refresh token came back.** `access_type=offline` with `prompt=consent`
   returned one, 103 characters, stored encrypted. This is the single most
   load-bearing unknown in the task, because `T-151`'s entire daily command is
   pointless without it.
4. **The access token carried exactly `drive.file`**, and `expires_in` was
   3600, so `expires_at` landed an hour out — which is what
   `REFRESH_MARGIN_MINUTES` of 5 was sized against.
5. **`about.get` answered an `external_id` of 20 characters**, the
   `permissionId`, and an `account_name`. The identity read works against a
   real account and not only against `about-get.json`.
6. **The refresh works with Qori's own client secret**, which the Playground
   fixtures could not test: `GoogleAccounts::refresh()` on the stored token
   answered `isRenewed()` true, a fresh 253-character access token, the same
   single scope and another hour. Google returned **no** new refresh token, so
   `tokensFrom()`'s fallback kept the stored one — exactly what case 22,
   `test_a_refresh_without_a_new_refresh_token_keeps_the_old_one`, asserts.
7. **`login_hint` is a hint and not a constraint.** The owner was offered an
   account chooser despite the hint naming one address, and connected a
   different Google account from the one Qori suggested. The row named the
   account actually chosen, which is the correct behaviour and worth knowing
   before `T-092` builds on the same parameter for a Peer's identity.

**Still not recorded:** the Cloud app's publishing status at the time of the
run. It decides whether every refresh token dies after seven days
(https://support.google.com/cloud/answer/15549945), so it matters to `T-151`
rather than to this task's code, and it is one line in the Cloud console. The
consent screen carried no "Google hasn't verified this app" warning, which is
suggestive but is not the same as having read the setting — left unstated
rather than guessed.

**The connection was left in place** on the local dev database, pointed at the
owner's real Google account. With the tag reverted, the Integrations page no
longer draws the section, so there is no button to remove it: it goes with
`Connection::query()->where('provider', ConnectionProvider::GoogleDrive)->delete()`
inside `CurrentGroup::runFor()`, or by re-adding the tag line locally and
pressing Disconnect. Removing Qori from the account's third-party apps at
Google's end is the owner's to do there, and nothing here did it.

## Where the specification was wrong

Three defects, all recorded under the task's Notes with the same detail. In
every case the Scope was satisfied and nothing about what was built changed.

1. **Tests 3 and 4 cannot both hold.** Case 3 wants a tier not belonging to the
   provider refused by validation; case 4 wants Zoom, which names no
   `ProviderTier` case at all, refused by the Service with
   `errors.connections.not_available`. Narrowing the rule to
   `ProviderTier::forProvider()` unconditionally makes Zoom 422 on every value
   before the Service can answer. Built: the rule narrows when the provider
   offers tiers and falls back to a plain enum rule when it offers none, so a
   provider with no tier gets the honest answer rather than a field error about
   a dropdown nobody was shown.
2. **Cases 35 and 37 each ask for two things one request cannot both do** —
   "302 to Integrations" _and_ "`ConnectionsDestination::KEY` taken". With a
   forwarding address present the redirect goes there, which is what the
   Decisions paragraph requires. The two readings were split across the cases
   rather than a third behaviour invented; every clause is covered, but no
   single request asserts both, because none can.
3. **Tests 2, 14 and 19 expect 403, which a form POST never gets.**
   `AppException::render()` (`app/Exceptions/AppException.php:248-288`) returns
   a status response only when the request expects JSON or the method is `GET`;
   otherwise it flashes a toast and returns `back()`. That is the app's global
   behaviour and not this task's to change. Those cases use
   `postJson`/`deleteJson`, which satisfies the spec literally.

## Found, not fixed

- ~~`app/Http/Controllers/Share/IntegrationsController.php:51` counts priced
  Series with no explicit group scope, which may be a cross-tenant leak in the
  Stripe disconnect warning.~~ **Checked the same day and it is not a defect —
  I was wrong to suspect one.** The reconnaissance sheet flagged the bare
  `Series::query()` and I took it at face value; reading it properly shows
  `Series` uses `BelongsToGroup` (`app/Models/Series.php:49`),
  `GroupScope::apply()` (`app/Models/Scopes/GroupScope.php:22`) adds the
  `group_id` predicate, and the route sits inside
  `middleware(['auth', 'verified', 'group'])` (`routes/share.php:25`), so the
  context is set before the controller runs. It fails closed, not open: with
  no context `idOrFail()` throws rather than counting every Group. And the
  regression test this would have asked for already exists —
  `tests/Feature/Share/PaymentsDisconnectTest.php:153`,
  `test_the_page_counts_priced_series_for_the_dialog()`, puts a fourth priced
  Series in a second Group and asserts the prop is 2, so an unscoped count
  would answer 3 and fail it. The bare `::query()` is the house idiom on a
  group-scoped model, about thirty times over, and `CLAUDE.md`'s tenancy rule
  is that the trait is the guarantee precisely so callers need not restate it.
  → decided: nothing to fix and nothing to test; the suspicion is recorded in
  `T-153` so the next reader of that line does not spend the same hour on it.

- `resources/js/pages/share/settings/Integrations.vue:141-154` carries a

  → decided: a comment, not behaviour; it will go the next time that file is
