# T-036 — report

## Outcome

Sign-in is one composition with one email field. Password and Email link are a
visible two-way choice; each panel owns its own form, its own errors and its own
button; and the address survives switching between them because both panels bind
to the same value and only the chosen one is mounted. Asking for a link replaces
the form with a confirmation naming the address. Passkey moved below the whole
composition and lost nothing. The exit to registration is now at the bottom,
once.

The page previously carried **two** fields both labelled "Email address" with
the same placeholder, separated by that registration link. It has one.

## Verified

Browser, `localhost:8001`, dark and light, 800px and 375px:

| What                               | How                                                                             | Result                                                                                 |
| ---------------------------------- | ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| One email field                    | `document.querySelectorAll('input[name="email"]')` while showing the link panel | **One**, id `link-email`                                                               |
| The address survives the switch    | Typed into Password, switched to Email link                                     | Carried over, character for character                                                  |
| Manual activation                  | Focused the second trigger, dispatched `ArrowLeft`, read state                  | Focus moved to Password; **Email link stayed the active panel**                        |
| The confirmation state             | Requested a link                                                                | "Check your email", the neutral sentence, the address, resend, "Use a different email" |
| The selected tab reads as selected | Both themes                                                                     | Correct after a fix — see below                                                        |
| Passkey                            | Still on the page, below a rule                                                 | Reachable                                                                              |
| 375px                              | Dark                                                                            | No overflow                                                                            |

The keyboard check is the one worth having done in a browser. The test asserts
the default is written in the component; only the browser says Reka honours it.

## Where the specification was wrong

| Section | Said                                                      | Actually                                                                                                               |
| ------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Files   | `ui/tabs/Tabs.vue` and `index.ts`                         | A usable tab set is four components. `TabsList`, `TabsTrigger` and `TabsContent` were added, matching `ui/collapsible` |
| Files   | Did not list `FortifyServiceProvider.php`                 | Two new lang keys have to reach Vue somehow, and the login view is where its props are built                           |
| Files   | Did not list `PasskeyVerify.vue`                          | It renders a hardcoded "Or continue with email" rule that only makes sense above an email form                         |
| Tests   | `test_the_page_has_one_email_field` counts `name="email"` | Counting answers the wrong question once each panel has its own and only one mounts — see below                        |
| Tests   | "existing auth tests should not need changes"             | One did: `TabIndexTest` reads `Login.vue` for the tabindex note, and the note followed the fields                      |

**The count is not the property.** With the fields inside tab panels, a static
count of `name="email"` in the source is two and in the DOM is one. What makes
that one address rather than two is that every field binds to the same ref, so
the test asserts the count of `name="email"` equals the count of
`v-model="email"`, and separately that `Login.vue` declares no field of its own.
Those two together say what the spec meant.

**The spec's stop condition was read and judged not to apply.** It says that if
an existing auth test needs changing, "the composition has moved behaviour
rather than layout — stop and re-scope". No behaviour moved.
`TabIndexTest::test_the_rule_is_stated_where_somebody_will_meet_it` asserts that
a _comment_ lives in `Login.vue`, and the comment is attached to the fields
rather than to a filename, so it moved with them into `SignInMethods.vue`. The
test now reads the file that has the fields. Pinning it to a page with no fields
on it would have been the rule surviving in name only.

## Departures

- **Three more tab components**, following `ui/collapsible`'s shape. Manual
  activation is defaulted in the wrapper rather than passed at the call site, so
  the next set of tabs inherits the safer behaviour.
- **`PasskeyVerify` gained `separator?: string | null`.** Passing `null`
  suppresses the rule. The default is unchanged, so `ConfirmPassword.vue`, the
  other caller, is untouched.
- **The layout description changed** from "Enter your email and password below
  to log in" to "Choose how you would like to sign in". The old line named one
  method on a page now offering a choice; leaving it would have been the same
  defect in words.
- **`requested` is a separate flag from `status`.** `status` is a general
  session flash and other flows put their own sentences in it, so the
  confirmation needs both a request made on this page and a server answer.
  Showing "Check your email" for an unrelated status would be a confident lie.
- **The chooser's selected state is the lighter fill, not shadcn's default.**
  See below.

## Found by looking, not by a test

**The shadcn tab styling is inverted for this product.** Its default puts
`bg-background` on the active trigger over a `bg-muted` list. On Qori's dark
theme `background` is the darkest token, so the selected tab became the darkest
thing in the control and read as the one _not_ chosen — I watched the panel
change while the wrong trigger looked selected. Every other chosen-state in this
product is the lighter fill: the settings nav, the sidebar. The component now
matches them, and the reason is in its docblock so the next person does not
paste the default back.

No test could have caught it. The classes were applied correctly; the palette
made them mean the opposite.

## Found, not fixed

- **The layout description stays put in the confirmation state.** After a link
  is requested the page still says "Choose how you would like to sign in" above
  "Check your email". The choice has been made by then. The layout owns that
  line and this task does not.
- **The 2FA challenge is unexercised in a browser here.** It is out of scope and
  must keep working; `TwoFactorChallengeTest` passes, which is server behaviour
  rather than the screen.
