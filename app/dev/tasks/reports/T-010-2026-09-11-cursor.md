# T-010 — report

## Outcome

A creator can now get rid of a Series, and it takes a week. Asking marks a date
and deletes nothing; every surface that shows the Series starts carrying that
date — the creator's list, the Series page, the Peer's page and the public page
— and the creator can call it off until the day arrives. A scheduled command
sweeps whatever is past its date, deletes the Episodes and the files behind
them, and stops there.

What survives is the part that was never the creator's to remove. The Series row
stays as a tombstone, so every access, every `payment_reference` and every
certificate code stays with it, and a Peer who opens a Series whose material has
gone gets a page explaining that rather than a 404: "The Creator has taken this
Series down. Your certificate and your receipt are unaffected." Their
certificate still verifies, and the admin console still attributes the Series to
the Group that made it.

The one thing that does **not** work yet is the timer, and not for a code
reason: nothing on this machine or in production runs the scheduler. This task
adds Qori's first scheduled command, so `schedule:run` has to exist on a cron
before any of the above happens on its own.

**Could not verify:**

- **A real R2 deletion.** The dev disk is genuinely R2, and this working tree is
  shared with several other agent sessions, so every Episode in the browser pass
  pointed deliberately at a key that does not exist. The file deletion is proved
  by `Storage::fake()` in `test_the_sweep_deletes_the_stored_files` and by the
  already-gone path in `test_a_missing_file_does_not_stop_the_sweep`; **nothing
  in this attempt deleted a real object from a real bucket.** The task's second
  precondition is therefore still open.
- **The scheduler.** `Schedule::command('qori:series:purge')->daily()` is
  registered and the command runs correctly by hand, but there is no cron, no
  `schedule:run` and no `schedule:work` on this machine, so the sweep has never
  fired on its own — here or anywhere. The first precondition is unmet.
- **A paid Peer losing material in a browser.** Nobody has paid for anything on
  the dev database, so "the payment reference survives" is an assertion on the
  access row rather than something I watched a paying Peer keep.
- **Anything about scale.** The sweep loads every due Series into memory with
  `->get()`. That is right for the volumes Qori has and I have not tested it
  against a large backlog.

**The two unnamed test changes matter more than they look.**
`ConsoleAccessTest` enforces an allow-list of files permitted to call
`acrossAllGroups()`, and this task deliberately adds the third crossing — so
the command had to be added to that list, which is exactly the review the
allow-list exists to force. `ModelEnumTest` carried
`'SeriesStatus::Purged' => 'T-010 — the purge sweep is not built'`; leaving it
there would have been a promise still outstanding after it was kept.

## Departures

- **`SeriesStatus::live()`**, a new static returning the cases where
  `isLive()`. `scopeUnarchived()` was `where('status', '!=', Archived)`, which
  was correct for one excluded status and silently wrong for two. It now asks
  the enum. This is the "one line in one place" the spec wanted, just asked of
  the enum rather than restated in the scope.
- **A separate `Panel` for deletion** rather than putting the controls inside
  the archive panel the spec pointed at ("in the panel `T-009` added"). It sits
  immediately below it, at the foot of the page as intended, but archiving and
  deleting make different promises and one panel cannot carry both titles.
- **`errors.series.already_purged` is thrown from `requestDeletion()` and
  `cancelDeletion()`.** The Copy table asks for the key and nothing in the spec
  says who throws it; a key with no thrower is the disease `T-023` removed from
  this same lang file.
- **One fix found in the browser, not by a test.** The Peer's episode panel fell
  back to its empty state, "Whoever shared this hasn't added any Episodes to it
  yet" — true of a Series still being made and a lie about one that has been
  taken down. The page now drops that panel entirely when the Series is purged,
  so the notice above is the only answer. No test could have caught this: every
  assertion about that page was about props, and the props were right.

## Found, not fixed

- **`media_assets` rows outlive the objects the sweep deletes.** A purged
  Episode's file is gone from the bucket while its `media_assets` row still says
  `stored` and still holds the key. The Scope explicitly defers this ("purging
  `media_assets` that no Episode references — a separate sweep"), so it is
  untouched — but the row is now not just unreferenced, it is **wrong**, which is
  a slightly worse starting point than the one that task was written for.
- **A purged Series is still reachable by URL on the creator's side.** It is
  gone from the list, but `/g/{group}/series/{slug}` still renders for it, and
  the page offers the archive and delete panels for a Series with nothing left to
  archive or delete. Nothing links there and the actions refuse, so it is cosmetic
  — but it needs a task.
- **`User::$fillable` excludes `email_verified_at`**, so `firstOrCreate` with a
  verified timestamp silently creates an unverified user. This cost me a browser
  round trip and it will cost the next person one; it is a seeding footgun rather
  than a product bug.
- **The dev environment cannot support a multi-step browser scenario right now.**
  Several agent sessions share this working tree and the `qori` dev database, and
  during this attempt one of them rebuilt it mid-pass — my seeded Group vanished
  between two steps, and a Series was purged by something outside this session.
  Worth knowing before anyone writes a task that depends on dev-database state
  surviving twenty minutes.
