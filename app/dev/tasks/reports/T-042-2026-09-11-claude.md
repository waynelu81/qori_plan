# T-042 — report

## Outcome

Both multi-row writes in `SeriesService` are transactional, and the comments
that said they did not need to be are gone. A failure part-way through removing
or reordering Episodes now leaves the Series exactly as it was, instead of
leaving positions reading 1, 2, 2 or a published Series quietly unpublished with
its only Episode still in it.

## Verified

The four new cases were run **with the transaction removed** as well as with it,
because a test that passes either way proves nothing about atomicity.

| Case                                                  | With the transaction | Without it                                 |
| ----------------------------------------------------- | -------------------- | ------------------------------------------ |
| `test_removing_an_episode_closes_the_gap`             | Passes               | Passes — the happy path never needed it    |
| `test_a_failed_renumber_leaves_no_hole`               | Passes               | **Fails**: 3 Episodes survive instead of 4 |
| `test_reordering_is_all_or_nothing`                   | Passes               | **Fails**: order left as 1, 3, 2           |
| `…_removing_the_last_episode_of_a_published_series_…` | Passes               | **Fails**: Series left unpublished         |

The failure is injected through an Eloquent model event rather than a mocked
connection, so the rollback being tested is a real Postgres savepoint.

## Where the specification was wrong

| Section | Said                          | Actually                                                                                                                     |
| ------- | ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Why     | Four places claim embedding   | **Eight.** The four it named, plus `Series.php`'s class docblock, a route comment, the Series factory, and a test's own name |
| Why     | "one of them is load-bearing" | Two were. The third place that mattered was a **test**, which is worse: it looked like proof                                 |
| Files   | Four paths                    | Nine. The five added are in the task's Files table under "Added during execution"                                            |

**The test was the interesting one.** `test_episodes_are_embedded_and_ordered`
finished with a comment reading "Embedded means they live in the series
document, not a collection" and this assertion:

```php
$raw = Series::query()->acrossAllGroups()->where('id', $series->getKey())->first();
$this->assertCount(2, $raw->getAttribute('episodes'));
```

It passes, and it has always passed, because `getAttribute('episodes')` on a
model with nothing eager-loaded **lazy-loads the relation** rather than reading a
column. The test could not tell the two storage designs apart and read as though
it could. It now asserts `series` has no `episodes` column and that the rows are
in `episodes` with the right `series_id`, which is a claim only one of the two
designs can satisfy.

**`Series.php` contradicted itself within ninety lines.** Its class docblock said
episodes were embedded and edits were "atomic without reaching for a
transaction"; the docblock on `episodes()` said "a real relation now, not an
embedded subdocument". Both were committed, and the true one is the one nobody
quotes.

**A dead docblock was sitting above `episodes()`**: `@return EmbedsMany<Episode,
$this, Collection<int, Episode>>`, immediately followed by a second docblock.
PHP takes the adjacent one and PHPStan reads the same, so a return annotation
naming a class that exists nowhere in this codebase analysed clean. Removed.

## Found, not fixed

- **`SeriesService::addEpisode()` reads `position` from a stale relation.** It
  computes `$series->episodeCount() + 1`, and `episodeCount()` reads
  `$this->episodes`, which Eloquent caches on the instance after the first
  access. Two calls against the same instance therefore both produce position 1,
  and `guardEpisodeLimit()` has the same blind spot, so a caller in that shape
  could also pass an episode cap it has already reached. **No production path
  hits it today**: every HTTP caller resolves the Series once per request and
  adds one Episode. It cost this task a wrong test fixture, and it will cost the
  same to the first code that adds two Episodes in one request — a seeder, an
  import, or the guided first-Series flow in `T-026`. Out of scope here, which
  named only the two multi-row writes.
- **`AccessService` and `CheckoutService` have not been read.** The spec
  excluded them and they may have the same shape. That is the sweep the Scope
  defers.
