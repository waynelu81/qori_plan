# T-078 — report

## Outcome

The Group has no `name_set_at`. Whether its name has been chosen is the
owner's onboarding record, `onboarding_state.name === 'done'`, written by
`GroupService::rename()` whoever typed the name and read by
`Group::hasChosenName()`, which every caller still asks. `User::onboardingNext()`
treats the name like storage — answered when the record has a key — and keeps
one fact that outranks the record, the connected account. A skipped name stays
not chosen, so the dashboard keeps asking. The migration carried every named
Group to its owner's record before dropping the column; in the dev database
the owner's record went from payments and storage skipped to those two plus
`name: done`.

## Departures

- **`OnboardingService::record()` reads the stored record before merging.**
  One extra query per write, and a stale copy can no longer clobber a fresher
  answer. This is what made `SetupTest::test_a_named_group_signs_in_to_its_dashboard`
  pass unchanged: it skips two parts on a copy that never saw the rename.
- **Three tests refreshed the person or assert the new rule.**
  `OnboardingHomeTest::test_the_group_home_sends_its_owner_to_setup_too` and
  `SetupStepsTest::test_an_owner_resumes_at_the_first_unfinished_part` read the
  owner again after a service-level rename, as a request would.
  `SetupStepsTest::test_existing_owners_are_not_sent_back_through_setup`
  asserted that a person with an empty record is sent to payments when the
  Group's name is a fact; the name is not a fact now, so it asserts that such
  a person is asked for the name, and one whose record answered it moves on.
- **`npm run check:fix` before every commit that adds markdown.** The gate
  first failed on Prettier for three files committed earlier without it: this
  task's spec, `T-079`'s, and `T-077`'s report. All three are formatted in
  this commit. Nothing in the process names the step for planning-only
  commits; it should.

## Found, not fixed

- **A test's `actingAs()` holds one instance across requests.** A write to a
  different instance of the same person is invisible to that test's next
  request, where a real request loads the person afresh. Two tests here met
  it; a `TestCase` note, or a helper that re-reads the acting user between
  requests, would stop the next person debugging it from scratch. → decided:
  not a task — it is how Laravel's `actingAs()` works, and `OnboardingService`
  now reads the person afresh before each write (`recordName()`, `finish()`),
  so the product no longer depends on which instance a caller holds (triaged
  23 September 2026)
- The dashboard's rename card still reads "Name your Group" after the name
  is chosen (`T-075`'s report). Triaged 23 September 2026 → T-086
- `docs/planning/walkthroughs.md` still narrates `name_set_at`; that is
  history and was left alone. → decided: history is never rewritten, and this
  report says when the column went (triaged 23 September 2026)
