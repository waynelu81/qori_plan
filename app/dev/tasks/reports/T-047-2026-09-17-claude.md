2, 3, and the plan's episodes-per-series cap counts every one of them.

one Series, and their fixtures now get real positions instead of all 1.

## Departures

- `EpisodeOrderTest` gained two private helpers, `emptySeries()` and
  `addEpisode()`, which the fixture and both new cases share.
- The new cases load the Series' Episodes first (`->load('episodes')`), so they
  test a Series that already has its list loaded whether or not `add()` loads
  it.
- The cap test also checks the refusal's developer message names the
  episodes-per-series limit, because the over-cap lock refuses with the same
  `PlanLimitReached` code.
- `guardEpisodeLimit()` returns before counting when the plan has no cap, so
  uncapped plans, which is every plan today, run no extra query.

## Found, not fixed

- With the Series' Episodes loaded before an add, the same instance still
  misses the new Episode afterwards: `SeriesService::publish()` refuses with
  `no_episodes` (`app/Services/SeriesService.php:157`), and
  `EpisodeService::remove()` (`:170`, `:188`) and `reorder()` (`:220`)
  cannot find it. A reviewer confirmed all three with a throwaway test. The
  spec's Out list named `AccessService` and `CampaignService` for this sweep,
  not the two services beside `add()`
  → draft T-117
- `add()` counts and then inserts with no lock, and `(series_id, position)` is
  not unique, so two adds to one Series at the same moment can still share a
  position or both pass the cap. The spec's "It writes one row" misses the read
  before it
  → draft T-117
- `MailCheckCommand` publishes `$series->fresh()` after an add, and
  `docs/tinker/series.md` reloads between adds; neither is needed for a Series
  whose Episodes were never loaded
  → decided: both are still right for a caller that loaded them first, until T-117 settles the stale reads
