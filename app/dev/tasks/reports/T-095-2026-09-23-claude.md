# T-095 — report

## Outcome

The spike ran on 23 September 2026, from 11:43 to 15:20 AEST, entirely on free
accounts (`D-042`). The owner held the accounts and ran every probe in their
own terminal. I wrote the probes, read what they saved, and worked the Peer's
side in a browser signed in as the Peer.

**Step 0 met outcome A.** A free Basic account gave a Peer view-only access
on a shared folder and on a single file. The Stone spec's "Pro or Business"
for `add_folder_member` did not bind a Basic account, so nothing had to be
bought and every later step ran on `creator-basic`.

**The recommendation is the file route, and the owner took it** (`D-058`,
Dropbox's counterpart to `D-036`). The folder route works, and costs every
buyer in ways a file does not:

- joining a folder counts its whole size against the Peer's own Dropbox;
- Dropbox shows joined Peers to each other ("your name, email address and
  activity are visible to other people with access");
- the creator's member list cannot tell a joined Peer from one who has not
  joined;
- `add_folder_member` answers `null` whether it granted anyone or not;
- a shared folder inside a shared folder is allowed and inherits every
  member, where the spec expected a refusal.

A file grant answers with the level it gave (`success: viewer`), costs the
Peer nothing, needs no Join, and its `preview_url` opens the Episode directly
for the Peer. `T-096` reuses `T-160`'s `GrantsItemAccess` for it.

**The whole journey ran on `T-096`'s own four scopes**: grant by `dropbox_id`,
open, later content, a repeated grant, and a revoked token recovered by
signing in again. A token without `files.content.write` cannot write to a
creator's storage; Dropbox refused the upload with `missing_scope`.

There are 63 fixtures in the code repository's `tests/Fixtures/dropbox/`,
redacted by role, each with its call, status and seconds in the README there.
The owner judged the remaining steps not applicable (`D-058`). Two of them
bear on files as well as folders — a team admin's outside-sharing policy and
the invite cap — and `T-096` carries them as not observed.

## Found, not fixed

- A viewer of a Dropbox file or folder is offered Download, and of a folder
  Copy to Dropbox, so a Peer can keep what they were given; `T-096`'s copy has
  to say so where it says what a buyer gets. → T-096
- A removed Peer who reloads is offered Dropbox's own "Request access" button,
  which asks the creator directly, outside Qori; a creator should expect such
  requests and know that granting one bypasses Qori. → T-096
- The file route's revoke, `remove_file_member_2`, and `list_file_members`
  paged with `limit: 1` were not observed, and neither was whether a file's
  viewers can see each other, which is the privacy question the folder route
  failed. `T-096` cannot be ready without the first two, and the third decides
  its buyer copy. → T-096
- A file granted directly stays granted when the creator shares or moves it
  into a folder of their own, where Dropbox lists the Peer only as inherited,
  and removing the Peer from that folder left the file grant standing. A
  revoke under `D-038` removes the file member Qori made whatever the list
  shows. → T-096
- Dropbox returns no `nonce` in the id token, so `T-092`'s Peer sign-in cannot
  use one against replay; `state` and PKCE carry it, and whether Dropbox
  accepts PKCE was not observed. → T-096
- The token refresh answers only `access_token`, `token_type` and
  `expires_in`, so `account_id` is kept from the first exchange; and revoking
  one token leaves the app's other tokens for that account valid, so a
  disconnect revokes the one Qori holds. → T-096
- Dropbox shows every creator and every Peer "Before you connect this app… This
  app only has a small number of users" at each sign-in while the app has few
  users, including an account that has linked it before. `T-096`'s connect
  screen and `T-092`'s sign-in should prepare them for it. → T-096
- Dropbox allows a shared folder inside a shared folder, inheriting every
  member. `D-058` removes Dropbox's folder; a container model that stays for
  another vendor cannot rely on the vendor to refuse nesting. → T-091
- The name "Qori" is held by an app not listed in Dropbox's App Center, and an
  app's name cannot change once it has production status; the app is `Qori
  Share` until then. → decided: recorded in `release-prerequisites.md`'s
  Dropbox line, where the owner can ask Dropbox support before applying
- The spike left `/Qori spike` (with `nested` and five episode files) and
  `/episode-file-route.pdf` in the owner's real Dropbox, grants to
  `peer-roomy`, `peer-none` and `spike-walk`, three linked authorizations of
  `Qori Share`, and tokens in the session's scratchpad. → decided: kept until
  the file route's open questions above have run on them; then the owner
  deletes the files and disconnects the app in the browser, and the scratchpad
  goes with the session
