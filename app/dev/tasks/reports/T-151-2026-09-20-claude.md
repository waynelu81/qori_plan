# T-151 — report

## Outcome

A creator's connection now keeps working without them thinking about it. A
daily `qori:connections:refresh` walks every Group, renews the tokens whose
connector refreshes on a schedule, and does it one row at a time under an
advisory lock; `ConnectionService::fresh()` renews on demand before a call
that needs a live token, which is what `T-091`'s `VendorAccessService` will
use inside a Peer's request. A token Google answers `invalid_grant` for is
marked at once, because it will never come back; anything else is counted and
the third failure in a row marks it, because a timeout is usually Google
having a minute. Either way the owner is emailed exactly once, on the call
that marks the row, so the next day's run and `T-091`'s vendor 401 add no
second email.

The lock now has an acquisition budget, which is the storage review's `F08`:
`AdvisoryLock::run()` sets `lock_timeout` inside the transaction and answers
`bool` — it took the lock and ran the callback, or it did not and did not — so
no request queues longer than the call it guards is allowed to take. A busy
lock counts no failure, because somebody else refreshing the same row is the
system working.

## Where the specification was wrong

1. **The Files table says "the five `mail.reconnect.*` lines"; the Copy table
   lists six.** Six were written, the Copy table being the one that names
   them.
2. **The Files table says "four constants" on `ConnectionService`; the Code
   block declares three.** The fourth, `SWEEP_TIMEOUT_SECONDS`, is `T-044`'s
   and was already there. Three were added.
3. **The spec has no test case for `fresh()`,** while its Acceptance box 3
   requires both `fresh()`'s margin behaviour and the shorter budget. That gap
   is what hid the bug below, and three cases were added to close it — see
   Departures.

## Departures

- **A real bug was found and fixed, and three test cases beyond the specified
  eight were added to catch it.** `fresh()` renewed nothing, ever.
  `isDue()` had been written as `$connection->expires_at instanceof Carbon`,
  but `AppServiceProvider:118` calls `Date::use(CarbonImmutable::class)`, so
  the `datetime` cast hands back a `CarbonImmutable`, which is not an
  `Illuminate\Support\Carbon`. The check was silently always false. It is now
  a null check with a comment saying why. The three cases —
  `test_fresh_renews_a_token_inside_the_margin`,
  `test_fresh_outside_the_margin_calls_nobody` and
  `test_fresh_passes_a_shorter_budget_to_the_connector` — started as a
  throwaway probe and were kept, because shipping a method that was broken
  five minutes ago and that `T-091` depends on, with nothing asserting it, is
  worse than a test count that disagrees with the spec. The file is 11 cases,
  14 across both new files rather than 11.
- **The notification's promoted property is `$account`, not `$connection`.**
  `Illuminate\Bus\Queueable` already declares a public `$connection` — the
  queue connection — and a second of a different type is a fatal error at
  class composition that names neither the class nor the property. There is a
  comment on it so nobody helpfully renames it back.
- **`qori:mail:check` and its coverage test, two files the table forgot.**
  `MailContentTest::test_every_notification_class_is_covered_by_the_command`
  refuses a notification the command never sends, on the grounds that nobody
  has then read it — and this task adds the sixth. The gate caught it on the
  first full run, which is the rule working. The command now creates a
  connection and calls `ConnectionService::markForReconnect()`, through the
  service that owns the message rather than by constructing it, which is that
  command's own documented rule; `EXPECTED` moves from 7 to 8 and the sender
  map gains an entry. Recorded under **Added during execution**.
- **`AdvisoryLock`'s catch sits outside `DB::transaction()`,** not inside it.
  A failed lock acquisition leaves the transaction aborted, and the rollback
  is what clears it, so catching inside would leave the connection unusable.

## Found, not fixed

- **Every model in the app declares `@property ?Carbon` for a `datetime`
  cast, and every one of them is actually a `CarbonImmutable`** — 40 property
  lines across 17 models, `Connection`'s own `$expires_at` among them. PHPStan
  reads and believes those docblocks, which is exactly why it could not see
  the `fresh()` bug above. Nothing else in `app/` currently does an
  `instanceof` against them (`EpisodeService:287` correctly uses
  `CarbonInterface`), so there is no second live bug today — but the next
  person to write `instanceof Carbon` against a model attribute will get the
  same silent false, and static analysis will agree with them.
  → draft T-154
- **`markForReconnect()` sends its email inside the advisory lock's
  transaction.** The spec puts the mark and the email in one method, and the
  method runs under the lock, so a synchronous Postmark call happens inside a
  Postgres transaction that is holding a lock — and a send failure rolls the
  mark back, leaving `isLive()` true until the next daily run tries again. The
  blast radius is bounded: `AdvisoryLock::WAIT_SECONDS` is 3, so nobody queues
  behind it for long, and the retry is a day away rather than never. It stops
  mattering entirely once a real worker exists and notifications can be
  `ShouldQueue`. `T-018` chooses the production queue topology and is the task
  that unblocks it; a line naming this call site is now in that draft.
  → T-018
