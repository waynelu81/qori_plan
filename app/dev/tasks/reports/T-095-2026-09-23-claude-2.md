# T-095 — report, the file route's three gaps

## Outcome

The first report (`reports/T-095-2026-09-23-claude.md`) left three things
unobserved on the route `D-058` chose, and `T-096` needed them before it could
be ready: `remove_file_member_2`, `list_file_members` paged, and whether a
file's viewers can see each other. One probe answered all three the same
evening, from 21:10 to 21:15 AEST. It used the accounts and tokens the spike
left, on `/episode-file-route.pdf`, and the creator used `T-096`'s four scopes
throughout, so every call it made is one `T-096` can make.

**Removal works, and takes effect at once.** `remove_file_member_2` answered
`success` in under a second, with no job. The Peer's next call, 1.3 seconds
after the removal was sent, found no file: `access_error/invalid_file`.
Removing a Peer who has a Dropbox account carried the same "You don’t have
permission to perform this action." warning the folder removal's job did,
although the removal had worked; removing an invitee carried none. Repeating
the removal answered 409 `no_explicit_access` with an empty `access_details`,
so a retry after a lost answer is an error, and the empty list is what says
nothing is left. Granting the removed Peer again answered `success: viewer`,
and the Peer had the file back at the first check, 2.0 seconds later.

**The member list pages as the folder's did.** With `limit: 1`, four members
came on four pages, users and invitees counted together, and the last page had
no cursor.

**A file's viewers can see each other, but only through the API.** Signed in
as the Peer, dropbox.com showed no other member: the Share button was
disabled, Info named only the uploader, and Activity was empty. Yet
`list_file_members` with the Peer's own token returned the file's two other
Peers with their addresses, though not the owner. So `D-058`'s "no buyer shown
to another" holds for Dropbox's pages and not for its API, and `D-058` now
carries that correction, dated. The folder route shows buyers to each other
in Dropbox's own pages as well, so the comparison that chose files stands.
What changes is that `T-096`'s buyer copy cannot promise that buyers are
hidden from each other.

  with their addresses, so any app a Peer connects with `sharing.read` can
  read them, and no file policy in the spec hides them. `T-096`'s buyer copy
  must not promise otherwise. → decided: the owner, 23 September 2026:
  buyers are not told, and the copy neither mentions it nor promises the
  opposite; recorded in `T-096` and `D-058`
- Whether a Peer's token lists another Peer who has a Dropbox account, as it
  lists invitees, was not observed: the spike had one Peer account. Every Peer
  `T-096` grants has an account, because `T-092` grants by `dropbox_id` after
  sign-in, so this is the case that matters. It needs a second Peer account.
  → decided: the owner, 23 September 2026, did not pursue it
- `remove_file_member_2`'s `success` can carry a warning that reads like a
  refusal, so `T-096` decides by the answer's `.tag`, never by `warning`; and
  a repeat's 409 `no_explicit_access` with an empty `access_details` means the
  Peer is already removed. A non-empty `access_details` would mean the Peer
  still reaches the file through a folder the creator shared themselves, which
  `D-038` leaves alone. → T-096
- Whether a Google Drive viewer can list a file's other viewers was never
  asked, although `T-160` already grants per file on Drive. → T-094
- The same question for OneDrive, on the files `T-097` already grants in
  steps 0 and 2 to 4. → T-097
