# T-035 — report

## Outcome

Twelve positive `tabindex` attributes are gone from the two screens every
account passes through, and a test stops them coming back.

They were not reordering those forms. A positive `tabindex` moves an element
into a separate, document-wide sequence visited **before every other focusable
element on the page** — so the first Tab on the sign-in page landed in the email
field rather than at the top of the document, ahead of the skip link, the
navigation and the passkey button sitting directly above the form. The DOM order
in both forms already matches the visual order, so deleting the attributes is
what makes the tab order correct rather than what changes it.

`TextLink`'s `tabindex` prop went with them. Sign-in was its only caller, and
leaving it would have been an affordance for putting the defect back.

## Verified

| What                | How                                                         | Result                                       |
| ------------------- | ----------------------------------------------------------- | -------------------------------------------- |
| `composer ci:check` | Clean tree                                                  | 546 tests, 2355 assertions, PHPStan 0 errors |
| The rule            | `TabIndexTest` walks every `.vue` file under `resources/js` | No positive `tabindex` anywhere              |
| Nothing else broke  | Full suite                                                  | No other test touched these files            |

**Could not verify — and this is the important line.** Nobody has watched the
tab order. `T-022` is blocked on a browser that receives key events and renders,
and I probed that during this task: the pane still reports `document.hidden ===
true`, and while a `Tab` keypress was delivered without timing out, focus did
not land anywhere observable. So this fixes a defect that is provable by
reading, and it proves nothing about the resulting order by observation.

That is deliberate and it is why the argument for the change does not depend on
watching it: a positive `tabindex` is wrong on these forms whatever the observed
order turns out to be. `T-022` still owns tab order as a seen property and is
not closed, narrowed or unblocked by this.

## Departures

**A comment in `Login.vue` explaining why the fields are unnumbered.** The spec
asked for a test asserting the comment exists, which implies the comment, but did
not write it. It is there because a rule enforced only by a test in another
directory is a rule the next person breaks in good faith and then argues with.

## Found, not fixed

- **`T-022` may be less blocked than it looks, and may not be.** Key events now
  reach the page without the timeout that scrolling and screenshots still hit
  while the pane is hidden. That is not enough to call it unblocked: focus rings
  and the animation-gated dialog unmount that `T-022` names both need rendering,
  not just key delivery. Worth one deliberate probe by somebody with a visible
  browser rather than another guess.
- **No skip link exists.** This task's reasoning leans on positive `tabindex`
  jumping ahead of one, and while auditing that I could not find one anywhere in
  the layouts. If that is right, the tab order on every page starts inside the
  navigation. It belongs to `T-022` and I did not chase it.
